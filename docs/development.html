Development

npm run build      # Compile TypeScript to out/
npm run start      # Run the compiled game
npm run dev        # Build and run in one step
npm run debug      # Build and run in debug mode
npm run watch      # Watch mode for development
npm test           # Build, then run the test suite
npm run probe      # Build, then run a measurement probe

npm run probe with no arguments lists what there is to measure, and which flags each probe takes. The probes that fly a shot take a grid and a build:

npm run probe -- seen-versus-kill
npm run probe -- column --grid 205x50 --build browser
npm run probe -- free-flight --passes 2
npm run probe -- overlay-anchor

A flag the named probe does not read is refused rather than discarded. npm run probe -- overlay-anchor --grid 80x24 exits non-zero and says which flags that probe takes, because a figure quoted from a grid nothing read is a figure from a walk that never happened.

The table the rig checks a command line against lives in test/probes/probes.mjs, and test/probes.test.mjs reads it against the probes themselves: every probe takes exactly the flags listed for it, and the refusal is spawned end to end for its exit code. A probe that stops reading an argument fails the suite rather than going on accepting the flag in silence.

Reading a probe's argument list covers its contract with the rig and stops there, so every probe that calls the shared engagement is also run by the suite, on the smallest workload the rig can describe - one grid, one build, and the smallest --count and --passes it takes - with what it prints collected rather than printed. That is what reaches the calls themselves. The workload is named by its flags rather than by what they narrow, because --count is not one unit: it is the placement walk in column, frame-rate and seen-versus-kill, and the frame count in free-flight, whose rate walk and dark walk neither --count nor --passes narrows - --grid and --build are what reach those, cutting both from six build-and-grid pairs to one. A probe can pass the flag check and still be handing the engagement an argument list it no longer takes, which comes back as a dash in a table nothing is running; the figures a narrowed walk prints are worth nothing and none of them is read for its value, only for having arrived. overlay-anchor is left out, because it imports no engagement to reach and reads no flags to be narrowed by.

Line Endings

Everything in the repository is LF, pinned by .gitattributes rather than left to whichever editor writes a file last. Git normalizes on the way into the index, so an editor that writes CRLF still commits LF and a diff stays the size of the change rather than the size of the file. The file is tracked, so a clone needs nothing configured.

Adding a new dotfile is the one thing that can need a local step. A global excludes file of the .* kind will hide it, and how you find out depends on how you staged it: git add <file> names the path, so git refuses it out loud and points at -f, while a bulk git add . or git add -A passes over it without a word. The quiet case is the one to watch for - if a dotfile you thought you staged never appears in git status, check it with git check-ignore -v --no-index <file> and stage it with git add -f <file>.

Tests

The suite uses the Node built-in test runner and adds no dependencies. It covers both builds, the agreement between them, the documentation site, and the measurement rig. The site is checked as the text of its own files, which needs no browser: its menu, its palette, the geometry of the fixed bar in both layouts - the tallest child it holds against the height it declares, and whether an in-page anchor lands clear of it - the two halves of the layout breakpoint naming adjacent widths, whether a dropdown list is shown in each layout and each state, which side the last group anchors its panel to, and every page published from a repository file carrying all of that file's prose and list items. The resolver those checks read the stylesheet through is pinned in turn by test/page-style.test.mjs, which weighs every shape of selector CSS counts differently and refuses the four functional pseudo-classes it does not model - a selector carrying one, and a whole sheet carrying one anywhere in it, since every reader here matches a selector whole and so misses such a rule rather than mis-weighing it. What it cannot decide from text is a drawn width, which needs font metrics: a browser is still the only thing that measures whether the nav's row of entries fits the width it switches on at.

The terminal tests import the compiled output from out/, which is why npm test builds first. The browser build is a single self-contained index.html with no module boundary to import, so those tests read the file and evaluate its inline script up to the point where it starts touching the DOM. Everything above that line is game logic and rendering, which is what gets exercised.

The pulse cannon checks run at three grid sizes rather than one: the 80x24 a terminal opens at, the 60x20 floor a small browser window is clamped to, and the 205x50 a full-screen window gives at the default font. The hit test is not size-neutral - a row is worth about two world units of height at 80x24 and about one at 205x50 - so a check pinned at one size can pass while the game a player sees misses.

Probes

A probe reports; it never asserts. The figures quoted in comments, tests and the changelog come from test/probes/, so a number can be rebuilt from the repository rather than taken on trust, and a number moving is something you read rather than a build that fails. Each probe prints its own method - the grid, the placement walk, the ship heights, the band and the frame rate - above its table.

The probes that fly a shot share one engagement with the tests, out of test/engagement.mjs, and run against the two real engines. A figure taken off a scratch copy of the engine can be right about the copy and wrong about the game.

overlay-anchor is the one that flies nothing. It measures where the browser build's touch controls land against the character grid underneath them, over every viewport the game will play at, so it takes no grid and no build - a terminal has no overlay, and the viewport is the thing being walked rather than a setting. It resolves the two control sizes out of the page's own stylesheet through test/page-style.mjs, which is the module test/browser-shell.test.mjs resolves them through as well: a probe with its own copy of a length goes on reporting about a rule the page no longer has, and this one's figures are quoted in the changelog.

Most of them stage that engagement - one target parked in an emptied run, the ship steered onto it - which isolates the shot, and is not the shape a fault turns up in. free-flight is the other end: a run the engine opens for itself, sixty obstacles in the tunnel and volleys overlapping, watched frame by frame, with the walk over the firing columns no flown engagement ever reaches printed underneath it.

Every walk here gives the same numbers every time. A staged walk always did, because it places what it flies; the run the engine opens for itself did not, because it drew its sixty obstacles from an unseeded Math.random. Quoting one of those passes put figures in this repository that the next run fell outside of, and restating them as spreads did not help - two ten-pass runs of the same walk disagreed with each other. So the engine takes a seed: seedRng pins every draw either build makes, both builds draw the same sequence from it, and free-flight flies a fixed set of seeded worlds. --passes N narrows it to the first N while you iterate; a figure quoted anywhere here is taken over the whole set, or at the first seed alone where the suite pins it, and each table says which. The game itself stays unseeded - a run nobody can predict is the point.
